# mr-review-agent

GitLab MR-агент на подписке **Codex** (не API). Тегаешь бота в комментарии к merge request —
он делает **ревью** по трём осям (баги, стандарты репозитория, соответствие постановке) или
**отвечает на вопрос** в треде. Работает под ChatGPT-подпиской (переиспользуем существующий
сиат через `auth.json`), от CI не зависит.

В примерах ниже бот назван `@codex`; тегать нужно то имя, что задано в `engines.<движок>.bot.username` файла `service.yaml`.

Самодостаточный сервис: свой `docker-compose` (бот + собственный Redis), общую инфру не трогает.

## Как это работает

```
GitLab (webhook: Note events) ──▶ POST /webhook (X-Gitlab-Token)
  └▶ Fastify: verify → parse → intent(@codex review | bugs | standards | spec | <вопрос>)
     └▶ BullMQ (server.queueConcurrency) ──▶ worker:
          clone→worktree(SHA) + чекауты смежных репозиториев
          → дифф (inline | agentic) → ось (src/queue/kinds/*): контекст и промпт
          → codex exec в песочнице / claude -p → разбор ответа → пост в MR
```

- `@codex review` / `ревью` / пустое упоминание → **общее ревью**: три оси ниже одним прогоном и одна
  заметка «Codex review» с разделами «Баги», «Стандарты», «Постановка» (см. «Общее ревью»).
- `@codex bugs` / `баги` → поиск багов, внесённых диффом: summary-заметка + inline-дискуссии по строкам.
  Замечания идут по важности (blocker → warn → info); тредами публикуется не больше пяти info,
  остальные — счётчиком в сводке.
- `@codex standards` / `стандарты` → сверка с задокументированными стандартами репозитория
  (`AGENTS.md`, `CONTEXT.md`, `docs/adr`, …). Нарушением считается только регрессия против живого
  требования: документ обязывает (цитата), проект сам этому следует (пример в коде до MR), отступление
  внёс этот MR. Запись без цитаты или примера бот отбрасывает. Нарушения — inline; правила, которым
  проект нигде не следует, и «запахи» (Фаулер) — списками в сводке.
- `@codex spec [PRJ-137 | #34 …]` → сверка с прямыми целями MR (ADR 0003): чек-лист требований и
  раздел «Сверх постановки». Прямая цель — ключ с префиксом из `issueKeys` профиля в заголовке MR,
  в имени ветки, в строке `Closes/Fixes/Resolves/Refs` описания или в аргументе команды. Нет цели —
  ось не запускается, заметка говорит, как её указать.
- `@codex <вопрос>` → ответ реплаем в тот же тред.
- Свои заметки игнорирует (анти-цикл). Проекты, не попавшие ни в один профиль `service.yaml`, игнорирует; в проекте отвечают только движки его профиля.
- На смёрдженный или закрытый MR отвечает одной строкой, что ревьюить нечего. Если пока шло ревью,
  в MR появились новые коммиты, после публикации добавляет предупреждение, что часть замечаний может
  быть неактуальна.

### Два режима диффа

Раньше дифф всегда вклеивался в промпт и резался по `MAX_DIFF_BYTES` — на большом MR
бот видел меньше половины изменений и рапортовал «Замечаний: 0». Усечения больше нет:

| режим | когда | что происходит |
|---|---|---|
| `inline` | дифф ≤ `review.maxDiffBytes` и ≤ `review.maxDiffLines` | тело диффа уезжает в промпт целиком, один проход |
| `agentic` | больше любого из порогов | тело **не отправляется вообще**; агент получает полный `git diff --stat` и чеклист файлов и вычитывает дифф сам (`git diff base..head -- <файл>`) |

В `agentic` агент обязан вернуть `reviewedFiles` / `skippedFiles`. По ним в шапке MR
печатается честная отметка: «просмотрено 34/34 файла» либо список непросмотренных с
дисклеймером. Бинарные файлы (скриншот-эталоны и т.п.) в чеклист и в счёт покрытия не
входят — построчного диффа у них нет.

Самоотчёту бот не доверяет на слово: на сотнях файлов агент читает выборочно, как бы
ни был сформулирован промпт. Поэтому оси «баги» и «стандарты» после ответа сверяются с
диффом, и непрочитанное уходит повторным прогоном той же оси — порциями по
`review.coverageFollowup.batch` файлов, не больше `review.coverageFollowup.runs` прогонов на ось.
Находки дописываются к первым; что не удалось дочитать, остаётся в плашке. Ось
«постановка» не дочитывается: её результат — чек-лист требований, а не находки по файлам.

Огромный дифф вообще не материализуется в память — решение принимается
по дешёвому `git diff --numstat`.

### Контекст требований

- **Смежные репозитории** (ADR 0005): документация, бэкенд для клиентского MR и прочий нужный
  агенту код перечисляются в `related` профиля (`{project, ref, hint}`). Бот выкладывает каждый
  полным чекаутом в `<jobdir>/related/<group>+<project>` рядом с worktree; агент грепает его
  целиком, а codex — и любую ветку (`git -C <каталог> show <ветка>:<файл>`) без сети: кэш — полный
  bare-клон, HEAD которого обновляется при каждом fetch. У claude `Bash(git show *)` такую команду не
  пропускает, ему доступна только выложенная ветка. `ref` — ветка (по умолчанию ветка репозитория по умолчанию) или `same-branch`:
  ветка с именем ветки MR, если она там есть, иначе ветка по умолчанию. Недоступный репозиторий
  или ветка не роняет джобу — попадает в «Неполные источники».
- **Коннекторы** (ADR 0002): Linear, GitLab и любая другая система подключаются записью в
  `connectors` файла `service.yaml` — готовый MCP-сервер (stdio-команда или URL), токены по
  `secret:NAME`, необязательный список инструментов `tools` и подсказка `hint` для промпта.
  Профиль проекта перечисляет, какие коннекторы доступны в его проектах. Бот переводит записи в
  настройки движка: у codex — `-c mcp_servers.<имя>={…, enabled_tools, default_tools_approval_mode="approve"}`,
  у claude — `mcp.json` + `mcp__<имя>[__<инструмент>]` в `--allowedTools`. Своего кода под
  конкретную систему у бота нет. Защита от записи — токен только на чтение на стороне системы;
  `tools` лишь убирает из выдачи агенту лишнее.
- **Сам MR**: описание и все треды целиком бот кладёт файлами в `<jobdir>/mr`
  (`description.md`, `threads.md`); в промпт треды попадают срезом.
- **Прямые цели** (`spec` и ось постановки в `review`) бот скачивает сам, до запуска агента,
  как MCP-клиент коннектора: правило `prefetch` коннектора называет инструмент и шаблон аргументов
  (`{key}`, `{number}`, `{project}`), ответ кладётся как есть. Привязанные документы — то, что
  вернул тот же инструмент. Текст не обрезается: до `review.targetsInlineMaxChars` он в промпте,
  выше — в промпте оглавление, полный текст в `<jobdir>/targets`, и цели, по которым агент не выписал
  ни одного пункта, бот дочитывает повторным прогоном. Фон (всё прочее, что упомянуто) агент
  открывает сам через коннекторы. Нескачавшееся — в блоке «Неполные источники» заметки.
- **Картинки** из описания MR и из прямых целей бот скачивает в `<jobdir>/images` — только вложения
  своего GitLab (`/uploads/…`); картинки с чужих хостов (например, Linear) агенту недоступны.

### Повторное ревью и ответы автора

Треды MR (включая прошлые замечания бота и ответы на них) подкладываются во все режимы.
Ответ автора при этом — **довод, а не приговор**:

- «уже починил» → бот сверяет с текущим кодом; правки нет — поднимает снова со ссылкой на тред;
- «так задумано» → inline повторно не дублирует, но разбирает сам аргумент. Если тот не
  снимает проблему и она уровня `blocker` — находка уходит в раздел сводки
  **«🔁 Оспорено автором — считаю, что проблема остаётся»**, а не в новый тред.

Так автор не получает повторных дёрганий в том же месте, но и не может отключить блокер
одной фразой: раньше промпт велел уступать безусловно, а поскольку каждое ревью стартует
с нуля, одного «так задумано» хватало, чтобы находка исчезла навсегда.

Пока висит оспоренное, вердикт формулируется как «_Новых замечаний нет — но см. раздел об
оспоренном выше._», чтобы «0 замечаний» не читалось как «MR чист».

### Общее ревью

`review` исполняет одна сессия codex — **оркестратор**: она запускает по суб-агенту на ось и ищет повторы
между осями. Ни задания, ни результаты через пересказ оркестратора не проходят:

```
<jobdir>/review/bugs.prompt.md       ← бот: тот же промпт, что у команды `bugs`
<jobdir>/review/bugs.out.md          ← суб-агент: ответ оси с маркерами
…то же для standards и spec
```

Бот сам читает `*.out.md` и разбирает их парсерами осей, а от оркестратора берёт только общий вывод и
список повторов (`{ drop, keep }` по идентификаторам `ось:список:индекс`). Отсюда гарантии:

- оси без файла результата в заметке помечаются «не отработала» — молча пропасть ось не может;
- если сведение не пришло или не разобралось, оси публикуются как есть, с предупреждением о возможных повторах;
- повтор снимается только между разными осями; пункт чек-листа постановки остаётся в таблице, гасится лишь
  его inline-тред;
- ось постановки не запускается, если источников требований не нашлось.

Разделы идут в фиксированном порядке и между собой не ранжируются. Оси идут параллельно, поэтому по
времени прогон короче трёх отдельных команд (на MR из 37 файлов — около 8 минут против 14), а по расходу
подписки — как три команды плюс оркестратор. Таймаут `engines.codex.timeoutMs` один на весь прогон.
Для движка claude `review` пока исполняется как `bugs`.

### Известные ограничения

- **Находки `standards` различаются от прогона к прогону.** Ось советующая: устойчиво ловятся явные
  нарушения, остальное зависит от прогона. Повторный запуск может дать другой набор.
- **Пример соблюдения (`precedent`) бот не перепроверяет** — только требует, чтобы агент его указал.
- **Каждый запуск стартует с нуля.** Память между прогонами — только треды MR.
- **Дочитывание пропущенных файлов вживую не наблюдалось.** На MR из 107 файлов агент с первого
  прохода отчитывался обо всех; цикл повторных прогонов проверен только модульными тестами.
- **Правило, которое только появилось в документе** и ещё нигде в проекте не применено, `standards`
  нарушением не посчитает: для него нет примера соблюдения.

### Сухой прогон

Проверить ось на реальном MR, ничего в нём не публикуя:

```bash
docker exec mr-review-agent node dist/cli/dryRun.js \
  --project acme/android-app --mr 163 --kind SPEC --out /tmp/dry-run/spec.md
docker cp mr-review-agent:/tmp/dry-run/spec.md .
```

`--kind`: `REVIEW` | `BUGS` | `STANDARDS` | `SPEC` | `ASK`; `--arg` — источники для `SPEC` или вопрос для `ASK`.
Чтения идут в GitLab по-настоящему, все записи (заметки, треды, реакции) складываются в файл.
Квота подписки при этом тратится как в боевом прогоне. Результаты содержат текст задач и код
проверяемого проекта — каталог `dry-run/` в `.gitignore`.

Если прогон упал, полный stderr codex можно получить переменной `CODEX_FAIL_LOG`:

```bash
docker exec -e CODEX_FAIL_LOG=/tmp/dry-run/fail.log mr-review-agent node dist/cli/dryRun.js …
```

### Что агенту доступно в git

Репозиторий выкачан в bare-кэш со всеми ветками (`+refs/heads/*` + merge-ref MR), а worktree
делит с ним объектную базу. Поэтому **локально и без сети** работают `git log <любая ветка>`,
`git show <ветка>:<файл>`, `git blame`, сравнение с любой веткой, вся история.

Чего агент сделать не может: `git fetch` (bare-кэш на запись закрыт — `Operation not
permitted`) и `git push` (плюс remote прописан без токена). То есть он работает ровно с тем
срезом репозитория, который выкачал бот.

> **MCP у codex работает только с `default_tools_approval_mode="approve"`** на каждом сервере:
> без него `codex exec` отклоняет каждый `tools/call` («requires approval, but approval policy is
> never»), а `"auto"` и `approval_policy="on-request"` не помогают. Проверено на codex 0.166.0;
> при обновлении codex проверку повторять (ADR 0002).

## Требования

- Docker + docker compose.
- **GitLab бот-юзер** с PAT (scope `api`) — от него постятся комменты. Его username = то, что тегают (`@codex`).
  Клонирует репозитории сам бот (не агент, песочница на это не влияет), и для клона хватает
  read-only доступа: роль Reporter + scope `read_repository`. Если хочется урезать права на
  клон — задай отдельный `gitlab.cloneToken` в `service.yaml`.
- **ChatGPT-подписка**: `auth.json` уже залогиненного Codex-аккаунта (`~/.codex/auth.json`).

## Быстрый старт

```bash
cp service.example.yaml service.yaml
# бот-аккаунты в engines, проекты в profiles
cp .env.example .env
# секреты, на которые ссылается service.yaml: WEBHOOK_SECRET (openssl rand -hex 32), GITLAB_TOKEN

# провижен подписочного auth.json в volume (переиспользуем существующий сиат):

docker compose restart codex-bot

curl -s localhost:8080/healthz | jq   # ждём {"status":"ok",...}
```

## Конфигурация

Настройки — в `service.yaml` (ADR 0004; шаблон с комментариями — `service.example.yaml`, путь — `SERVICE_CONFIG`):
движки и их бот-аккаунты, пороги ревью, коннекторы, профили проектов по glob. Секреты в файле не хранятся:
поля-токены принимают только `secret:NAME`, значение берётся из переменной окружения (`.env`). Ошибки
конфигурации — все сразу — сервис печатает при запуске и не стартует.

В `.env` — только секреты.
Отладочная `CODEX_FAIL_LOG` (путь к файлу) в `.env` не нужна — её задают на один запуск.

После правки `service.yaml` или `.env` контейнер нужно пересоздать: `docker compose up -d codex-bot`.
`docker compose restart` переменные не перечитывает.

### `.review.yml` в репозитории

Второй слой настроек (ADR 0004) — файл в корне репозитория. Бот читает его из **target-ветки** MR,
если она защищённая или ветка по умолчанию, иначе — из ветки по умолчанию: правка в самом MR
подействует только после мержа, а незащищённую ветку со своим `.review.yml` автор MR мог бы создать сам.

```yaml
connectors: [linear]            # только сужает коннекторы профиля
related:                        # добавляет смежные репозитории — только из relatedAllowlist профиля
  - { project: acme/backend, ref: same-branch, hint: API-контракты }
exclude: ["**/generated/**", "**/*.lock"]   # git glob от корня: в дифф и чек-лист не входят;
                                            # только латиница, цифры и _.-*?[]/
standards: [docs/style.md]      # ось стандартов читает их первыми
```

Секретов в файле не бывает. Любая ошибка — невалидный YAML, неизвестный ключ, коннектор вне профиля,
проект вне `relatedAllowlist` — и файл игнорируется целиком: ревью идёт по профилю, а бот пишет в MR,
что именно не так.

## Эксплуатация

- **Ротация сиата.** `auth.json` лежит на volume `codex-home` и рефрешится сам. Если сиат разлогинили/сменили
  пароль — `/healthz` уйдёт в `degraded`; перезалей свежий `auth.json` (см. «Быстрый старт») и `docker compose restart codex-bot`.
- **`/healthz` проверяет живость, а не наличие.** Сессия Codex — запросом лимитов через `codex app-server`
  (модель не вызывается, квота не тратится; результат кэшируется на 5 минут), GitLab-токены — `GET /user`
  (кэш 1 минута). Протухший токен любой роли (`codexBot`, `clone`) даёт `degraded` и 503 с причиной
  в `detail`. После замены токена кэш сбрасывается рестартом контейнера.
- **Срок GitLab-токенов.** У токенов GitLab есть срок действия (на gitlab.com — не больше года). После
  истечения `/healthz` покажет `Token is expired` у соответствующей роли; токен перевыпускается, значение
  меняется в `.env`, контейнер пересоздаётся.
- **Один сиат — один потребитель.** Если тот же `auth.json` используется ещё где-то (локальный codex
  разработчика, вторая копия бота), первая же ротация refresh-токена разлогинит остальных. Надёжнее
  отдельный `codex login` для бота.
- **Rate-limit.** Бот делит лимиты Codex с живым разработчиком (переиспользованный сиат). При упоре в лимит
  джоба не ретраится — бот пишет в MR «попробуйте позже». Лимит определяется только по строкам ошибок
  самого codex (`ERROR …`), а не по всему его выводу: там есть эхо промпта и вывод команд агента, и
  «429» или «quota» в тексте задачи иначе превращали бы обычный сбой в «лимит».
- **ToS.** Подписка в автоматизации — серая зона ToS OpenAI; сервис внутренний, read-only, под контролем команды.

## Безопасность

- **Окружение агента собирается по allowlist** (`src/agent/env.ts`), а не копированием
  `process.env`. `GITLAB_TOKEN`, `CLAUDE_GITLAB_TOKEN`, `WEBHOOK_SECRET`, `REDIS_URL`
  до агента не доезжают. Новая секретная переменная в `.env` по умолчанию тоже не доедет —
  чтобы её отдать, надо дописать её явно. (До этой правки README утверждал то же самое,
  но код делал `{...process.env}`, то есть утверждение было неверным.)
- Песочница: `codex exec --sandbox read-only` / `claude --permission-mode dontAsk` с белым списком
  read-инструментов. Коннекторам сеть агента не нужна: MCP-серверы ходят в сеть вне его песочницы.
  Полное снятие песочницы не используется никогда.
- **`agentNetwork: true` в профиле — ослабление**: codex идёт в `workspace-write` +
  `network_access`, claude получает `WebFetch`/`WebSearch`. Всё, что агент прочитал (в том числе
  текст задач и комментариев — канал prompt injection), он может отправить наружу.
  `cliTools` (например `[glab]`) разрешается только вместе с ней: claude получает `Bash(<tool> *)`.
- Общий `review` всегда идёт в `workspace-write`: суб-агенты пишут результаты осей в каталог
  джобы. Сеть при этом открывается только `agentNetwork`. Суб-агенты наследуют окружение, сеть и
  песочницу оркестратора.
- Токены коннекторов агенту не передаются через окружение: они уходят в MCP-процессы (у claude —
  `mcp.json` с правами `0600` в каталоге джобы, у codex — аргументом `-c`). Агент работает под
  тем же пользователем и при желании прочитает их, поэтому токен коннектора — только на чтение и
  от сервисного аккаунта с доступом лишь к нужным командам и пространствам.
- Источники постановки бот скачивает сам основным `GITLAB_TOKEN`. Сам токен до агента не доходит, но текст скачанных задач попадает в промпт и
  может быть процитирован в заметке MR.
  Границы по проектам здесь нет намеренно: и бот, и агент видят ровно то, что разрешает токен.
  Ссылку на источник пишет автор MR, поэтому бот может процитировать в заметке любую задачу,
  доступную токену, — в том числе конфиденциальную, которую сам автор MR не видит. Если бот обслуживает проекты с разной аудиторией, сужать нужно сам
  токен — токен проекта вместо личного токена бот-пользователя.
- **Quick actions GitLab обезврежены.** Строку заметки, начинающуюся с `/merge`, `/approve`,
  `/close` и т. п., GitLab исполняет от имени автора заметки, то есть бота. Текст заметок пишет
  агент, поэтому в `src/gitlab/client.ts` такие строки экранируются на выходе у всех заметок и
  тредов, включая строки внутри блоков кода: незакрытый блок в ответе агента иначе оставлял бы
  команду исполняемой. Цена — видимый `\/` в начале такой строки кода.
- **Песочница codex требует двух вещей в контейнере**, иначе она молча не работает:
  1. пакет `bubblewrap` (стоит в `Dockerfile`) — именно им codex делает sandbox на Linux;
  2. `security_opt: seccomp:unconfined` в `docker-compose.yml` — дефолтный seccomp-профиль
     Docker запрещает непривилегированные user namespaces, без которых `bwrap` не стартует.

  Без них `bwrap` падает с `No permissions to create new namespace`, и codex либо выполняет
  команды **вообще без песочницы** (в `read-only`), либо не выполняет их вовсе
  (в `workspace-write`). Проверить, что песочница реально включена:

  ```bash
  docker compose exec -T codex-bot sh -lc 'cd /tmp && \
    echo "Выполни: touch ./X && echo W=OK || echo W=DENIED" | codex exec --sandbox read-only -'
  # ждём W=DENIED; W=OK означает, что песочницы нет
  ```
- `git.cacheDir` обязан лежать **вне TMPDIR**: в режиме `workspace-write` агенту
  разрешена запись в TMPDIR, и кэш в `/tmp` стал бы для него writable. При `/data/repos`
  запись в кэш блокируется (проверено).
- Пишущие токены ботов агенту не отдаются никогда. GitLab для агента — такой же коннектор с
  токеном `read_api` (лучше project/group access token, а не personal PAT).
- Токен не сохраняется в git-remote кэша (передаётся только как аргумент fetch/clone).
  Для клона можно выдать отдельный read-only PAT (`gitlab.cloneToken`).
- У claude используется `--strict-mcp-config`, чтобы в прогон не подмешался MCP из настроек хоста.
- Timing-safe сверка `X-Gitlab-Token`; allowlist проектов.
